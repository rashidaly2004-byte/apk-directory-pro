A head worth copying

index.html — the head

<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">

  <title>Working with clay soil — Field Notes</title>
  <meta name="description" content="Why clay holds water, and three ways to
        improve drainage without replacing your topsoil.">
  <link rel="canonical" href="https://example.com/posts/clay">

  <link rel="icon" href="/favicon.svg" type="image/svg+xml">
  <link rel="apple-touch-icon" href="/apple-touch-icon.png">

  <meta property="og:title" content="Working with clay soil">
  <meta property="og:description" content="Why clay holds water, and how to fix drainage.">
  <meta property="og:image" content="https://example.com/img/clay-preview.jpg">
  <meta property="og:type" content="article">
  <meta name="twitter:card" content="summary_large_image">

  <link rel="stylesheet" href="/assets/styles.css">
</head>
TagWhy it's there
<title> Tab label, bookmark name, and the clickable line in search results. Put the specific part first: page name, then site name.
meta description The snippet under the title in search results. Around 150 characters. Doesn't affect ranking directly, does affect whether anyone clicks.
link canonical "This is the real address of this page." Prevents duplicate-content confusion when a page is reachable via several URLs.
link iconThe favicon. An SVG one covers light and dark modes and every size.
og:* / twitter:* Open Graph tags: the title, blurb and image used when your link is pasted into Slack, WhatsApp, Discord or a social feed. Without them you get an unappealing bare URL.
link stylesheetLoads your CSS. Goes in the head so the page doesn't flash unstyled.

Also worth knowing: <script src="app.js" defer></script> in the head loads JavaScript in parallel and runs it after the HTML is parsed — the sensible default. And <meta name="theme-color" content="#0f1420"> tints browser UI on mobile.

There is no meta keywords worth writing. Search engines have ignored it for well over a decade. If a tutorial tells you to add it, that tutorial is old.

Accessibility: the short list that covers most of it

You've already met all of these across the course. Together they handle the large majority of real-world accessibility problems in static HTML.

  1. Use the right element. A <button> for actions, an <a href> for navigation. Native elements are focusable, keyboard-operable and announced correctly for free; a div with a click handler is none of those.
  2. Set lang on <html>. It picks the screen reader's pronunciation.
  3. Every image gets an alt — descriptive, or empty if decorative.
  4. Every form control gets a <label>.
  5. Headings form a real outline. One <h1>, no skipped levels.
  6. Landmarks exist: header, nav, main, footer, and a skip link to main.
  7. Never remove focus outlines without replacing them with something at least as visible. Tab through your page and confirm you can always see where you are.
  8. Link text makes sense alone. No "click here".
  9. Don't convey meaning by colour alone, and keep text contrast high.

Where ARIA fits

ARIA attributes add accessibility information that HTML can't express on its own — aria-label, aria-labelledby, aria-current, aria-describedby, aria-expanded. They're useful, but the first rule of ARIA is: don't use ARIA if a plain HTML element already does the job. Adding role="button" to a div means you now have to reimplement focus, Enter, Space and disabled states yourself. Bad ARIA is worse than none.

Checking your work

  • The W3C validator — paste your markup and it lists unclosed tags, invalid nesting and misspelled attributes. Do this before you debug anything weird.
  • Dev tools (F12) — the Elements panel shows the tree the browser actually built, which is not always the one you typed. The Accessibility panel shows how your page looks to a screen reader.
  • Lighthouse, built into Chrome dev tools, audits accessibility, performance and SEO and links to explanations.
  • Your keyboard. Put your mouse down and Tab through the page. If you can't reach something, or can't see where focus is, that's a bug.

Habits that keep markup clean

  • Lower-case tag and attribute names; double-quoted attribute values.
  • Indent one level per nesting level. When you're lost in a page, it's almost always because the indentation stopped being honest.
  • Close every element, even the ones browsers let you leave open.
  • No inline style attributes in real work — put styling in a stylesheet.
  • No <center>, <font>, <marquee>, or align / bgcolor attributes. All long dead; CSS does all of it.
  • Prefer fewer elements. If a wrapper isn't doing anything, delete it.

Final project

Build a three-page personal site using only what's in this course, no CSS framework:

  1. index.html — a header with your name and a nav, a <main> with a short intro and a list of three things you've made as <article>s, and a footer.
  2. about.html — a photo with real alt text in a <figure>, a few paragraphs, and a table of skills or a timeline.
  3. contact.html — a properly labelled form with at least four fields, one <fieldset>, and required where it matters.

Every page shares the same nav, has a complete head with a description and Open Graph tags, and passes the W3C validator with zero errors. Then Tab through all three from top to bottom.

Where to go next

  • CSS is the obvious next step, and the payoff is immediate: your existing HTML suddenly looks like a real site. Learn the box model, then Flexbox, then Grid, then custom properties.
  • JavaScript after that, for behaviour.
  • MDN's element reference is the reference to bookmark. Every element, with examples and browser support. When you wonder "is there a tag for this?", the answer is usually there.
  • The HTML spec is surprisingly readable when you want to know exactly what's allowed inside what.
You now know enough. HTML has a couple of hundred elements and you will use thirty of them for the rest of your life. The remaining skill isn't more tags — it's choosing the right one, which only comes from building things.
