# Cursor Master Build Brief: Modern WordPress APK Directory Theme

## 1. Mission

Build a production-ready custom WordPress theme for an APK/app directory. The design should combine:

- APKFolder's simple, content-first app listings, compact metadata, and obvious download actions.
- APKPure's polished app-store feel, dense discovery experience, categories, search, version history, screenshots, ratings, and related-app navigation.
- The useful publishing workflow found in the supplied Appyn 2.0.17 theme, rebuilt cleanly with modern WordPress APIs and security practices.

Do not clone either reference site's branding, copyrighted artwork, HTML, CSS, or proprietary code. Create an original visual system inspired by their information architecture and interaction patterns. Do not modify or redistribute the supplied Appyn theme. Use it only as a functional reference.

Working name: `apk-directory-pro`  
Text domain: `apk-directory-pro`  
Minimum WordPress: 6.6  
Test through the current stable WordPress release.  
PHP support: 8.1–8.4  
License for original code: GPL-2.0-or-later.

## 2. Non-negotiable architecture

Create two installable ZIP packages:

1. `apk-directory-pro-theme.zip` — presentation only.
2. `apk-directory-core.zip` — companion plugin containing content types, metadata, ratings, download/version data, REST routes, migrations, and business logic.

Content must remain available if the theme changes. Therefore, never register app data or taxonomies in the theme.

Use:

- A classic PHP theme with `theme.json` and block-editor support. This gives reliable custom archive/single templates while keeping Gutenberg editing.
- Namespaced PHP classes with PSR-4 autoloading generated by Composer.
- WordPress Settings API, Metadata API, REST API, Transients/Object Cache API, WP-Cron, and Rewrite API.
- Vanilla JavaScript modules. Do not require jQuery on the front end.
- Modern CSS with custom properties, Grid, Flexbox, container queries where useful, and logical properties for RTL.
- Locally hosted system-font stack by default. No render-blocking Google Fonts.
- SVG icons bundled locally and output accessibly. Do not load a full icon-font library.

Do not use ACF, Elementor, Redux, Kirki, Carbon Fields, or another framework as a required dependency. Build native controls.

## 3. Lessons from the supplied Appyn theme

The supplied package is Appyn 2.0.17. It contains 3,058 files and about 24.6 MB uncompressed. Its relevant architecture includes:

- App post screens with version, size, requirements, release/update dates, developer, short description, OS, price, changelog, screenshots, YouTube video, ratings, downloads, and file links.
- App categories plus developer and separate blog taxonomies.
- Parent/child posts used as version history.
- Direct links, redirects, and locally hosted downloads.
- Live AJAX search, ratings, reports, view counting, related apps, most viewed, most rated, MOD listings, widgets, ads, dark mode, RTL, AMP, and download countdown pages.
- Homepage sections for top-rated apps, latest apps, selected categories, featured apps, MOD apps, and blog posts.
- A large custom options panel.

Rebuild those useful capabilities, but do not carry over these legacy decisions:

- Do not place all logic in a very large `functions.php`.
- Do not bundle full Google Drive or Microsoft Graph SDK vendor trees inside the theme.
- Do not store all app properties inside serialized arrays such as `datos_informacion` and `datos_download`.
- Do not model app versions as child blog posts.
- Do not use unbounded searches such as `posts_per_page => -1` for live search.
- Do not accept raw `$_POST` values, public AJAX mutations, file paths, ratings, or reports without nonce validation, permission checks, sanitization, validation, rate limiting, and output escaping.
- Do not disable native lazy loading globally.
- Do not inject arbitrary header/footer code by default.
- Do not create fake rating totals or view counts.
- Do not build a separate homegrown AMP theme. Keep markup fast and standards-based; allow an official AMP plugin to integrate if the owner chooses.
- Do not silently download APKs from third parties or automate scraping.

## 4. Content model (companion plugin)

### 4.1 App custom post type

Register `adp_app` with:

- Public archive slug: `/apps/`
- Single rewrite: `/app/%postname%/`
- REST support enabled.
- Supports: title, editor, excerpt, thumbnail, author, revisions, comments, custom-fields.
- Gutenberg enabled.
- Archive, search, sitemap, and feed support.
- An Apps admin menu using a custom app icon.

### 4.2 Blog posts

Use normal WordPress `post` for editorial/blog content. Do not create a second blog post type.

### 4.3 Taxonomies

Register:

- `adp_app_category` — hierarchical; Apps, Games, Tools, Entertainment, Education, Casino, etc. Archive `/category/app/{term}/` or a configurable base.
- `adp_developer` — non-hierarchical or hierarchical selectable; archive `/developer/{term}/`.
- `adp_platform` — Android, Android TV, Wear OS, Windows, macOS, iOS where appropriate.
- `adp_tag` — app-specific tags.

Add optional taxonomy metadata: icon attachment ID, color, short description, SEO intro, featured flag, and display order.

### 4.4 App metadata

Register every field with `register_post_meta`, REST schemas, sanitizers, authorization callbacks, and defaults. Prefix every key `_adp_`.

Core fields:

| Key | Type | Purpose |
| --- | --- | --- |
| `_adp_short_description` | string | One- or two-sentence summary |
| `_adp_package_name` | string | Example `com.example.app` |
| `_adp_current_version` | string | Human version name |
| `_adp_version_code` | integer | Android version code when known |
| `_adp_file_size_bytes` | integer | Store bytes, format only at output |
| `_adp_android_requirement` | string | Example Android 8.0+ |
| `_adp_architectures` | array | arm64-v8a, armeabi-v7a, x86_64 |
| `_adp_dpi` | array | nodpi or supported densities |
| `_adp_release_date` | date string | Original release date |
| `_adp_updated_date` | date string | Current release date |
| `_adp_price_type` | enum | free, paid, freemium |
| `_adp_price_amount` | number | Optional |
| `_adp_price_currency` | string | ISO 4217 code |
| `_adp_official_url` | URL | Publisher site |
| `_adp_store_url` | URL | Official Play Store/App Store URL |
| `_adp_support_url` | URL | Support page |
| `_adp_privacy_url` | URL | App privacy page |
| `_adp_license` | string | License when known |
| `_adp_content_rating` | string | Everyone, Teen, etc. |
| `_adp_status_badge` | enum | none, new, updated, mod |
| `_adp_verified` | boolean | Editor-verified record flag |
| `_adp_editor_rating` | number | Optional transparent editorial score |
| `_adp_download_count` | integer | Real tracked downloads only |
| `_adp_view_count` | integer | Optional, privacy-aware |
| `_adp_screenshot_ids` | array of integers | Media attachment IDs |
| `_adp_video_url` | URL | YouTube/Vimeo URL |
| `_adp_whats_new` | sanitized HTML | Current changelog |
| `_adp_mod_features` | sanitized HTML | Only if site policy permits MOD content |
| `_adp_disclaimer_note` | string | Per-app warning or provenance note |

Never store remote image URLs when the image belongs to the site. Use attachment IDs and WordPress image functions.

### 4.5 Version entity

Create a dedicated database table using `dbDelta`, for example `{prefix}adp_versions`:

- `id` bigint unsigned primary key
- `app_id` bigint unsigned indexed
- `version_name` varchar
- `version_code` bigint nullable
- `release_date` datetime nullable
- `changelog` longtext
- `min_android` varchar nullable
- `file_size_bytes` bigint unsigned
- `file_type` enum-like validated string: apk, xapk, apks, zip, obb
- `architectures_json` longtext
- `dpi_json` longtext
- `download_type`: media, external, redirect
- `attachment_id` bigint nullable
- `external_url` text nullable
- `sha256` char(64) nullable
- `signature_sha256` char(64) nullable
- `virus_scan_status`: unknown, pending, clean, warning, failed
- `virus_scan_date` datetime nullable
- `is_current` tinyint
- `download_count` bigint unsigned default 0
- `created_at`, `updated_at`

Add a repository/service layer. Do not scatter direct SQL across templates. Prepare every SQL statement. Enforce one current version per app in application logic and a transaction when supported.

### 4.6 Reviews and ratings

Use WordPress comments with a dedicated comment type `adp_review`, or a carefully designed custom table if necessary. Requirements:

- Rating 1–5.
- Verified email only if reviews are enabled.
- Moderation queue, anti-spam honeypot, rate limit, nonce, and privacy disclosure.
- One rating per user/app or per privacy-preserving browser token and time window.
- Never output aggregate rating schema unless real ratings exist and are displayed visibly.
- Editorial rating and user rating must be labeled separately.

### 4.7 Reports and takedown requests

Provide an app report form with reason, details, optional email, consent checkbox, nonce, honeypot, rate limit, and optional CAPTCHA integration through hooks. Reasons: broken link, outdated version, malware concern, copyright, incorrect information, other. Store reports in a private custom post type or table and notify an admin without exposing reporter data publicly.

## 5. Required plugin admin experience

### App editor sidebar/panels

Create accessible Gutenberg plugin panels for:

- App details
- Developer and platform
- Current version
- Download file and hashes
- Screenshots (sortable media gallery)
- Video
- What's new
- Safety/provenance
- Display overrides

Provide a classic metabox fallback if the block editor is disabled.

Validation rules:

- Package name pattern validation but allow an editor override.
- File size stored as bytes.
- Dates stored in a machine-readable format.
- URLs must use allowed schemes; block `javascript:`, `data:`, credentials in URLs, loopback/private-network SSRF targets where server requests occur.
- Uploaded file extensions and MIME types must match an explicit allowlist.
- APK upload permission requires a custom capability such as `upload_apk_files`; do not grant it to Authors by default.
- Show SHA-256 calculation status for local files.

### Version manager

Inside each App edit screen provide a version table with Add, Edit, Duplicate, Set current, and Delete. Deletion must require confirmation and must not delete a Media Library file unless the editor explicitly selects that option.

### Theme/plugin setup wizard

On first activation, offer—not force—the following:

- Create Home, Apps, Games, Blog, About, Contact, Privacy, Disclaimer, DMCA/Takedown, and Submit App pages.
- Assign menus.
- Import clearly labeled demo content.
- Configure permalinks by flushing rewrites once on activation only.

Never create pages on every request or theme switch.

### Import/migration

Build an optional Appyn migration tool that can map, after backup confirmation:

- Standard posts with `datos_informacion` into `adp_app` posts and registered meta.
- `descripcion`, `version`, `tamano`, `released_on`, `fecha_actualizacion`, `requerimientos`, `consiguelo`, `descargas`, `categoria_app`, `os`, `offer`, and `novedades` into the new fields.
- `datos_imagenes` into screenshot attachments when safely resolvable.
- `datos_video[id]` into a canonical video URL.
- `datos_download` into version rows.
- `dev` taxonomy into `adp_developer`.
- Parent/child Appyn posts into app/version records.

Migration must have dry-run preview, batching, progress, logs, resumability, idempotency, and rollback mapping. Never remove the original data automatically.

## 6. Original visual system

Create a clean app-store interface, lighter and more modern than the supplied Appyn screenshot.

### Design tokens

Use CSS variables and expose controlled theme settings:

- `--adp-primary: #18a957`
- `--adp-primary-dark: #128345`
- `--adp-accent: #2563eb`
- `--adp-bg: #f5f7fa`
- `--adp-surface: #ffffff`
- `--adp-text: #17202a`
- `--adp-muted: #667085`
- `--adp-border: #e4e7ec`
- `--adp-warning: #f59e0b`
- `--adp-danger: #dc2626`
- Radius: 10px small, 14px card, 18px large
- Shadow: very subtle; borders do most of the separation
- Content max width: 1180px
- Reading column: 760px
- Spacing scale based on 4px

Use a 16px base font, at least 1.55 body line-height, fluid headings with `clamp`, and minimum 44x44px touch targets. Meet WCAG 2.2 AA color contrast.

### Header

Desktop:

- White sticky header with a subtle bottom border.
- Left: custom logo.
- Center: large rounded search field with search icon and live suggestions.
- Right: primary navigation and optional dark-mode toggle.
- Secondary category bar below the main row, horizontally scrollable when needed.

Mobile:

- Logo, search button, and menu button on one row.
- Search expands into a full-width overlay or second row.
- Drawer menu traps focus, closes with Escape, has a visible close button, and restores focus.

### Footer

Use four responsive columns: brand summary, browse, company/policies, and optional newsletter/social links. Include copyright, disclaimer, and a compact language switcher hook. Do not claim files are safe or official unless verified.

### Dark mode

Support `prefers-color-scheme`, plus a user toggle saved locally. Ensure all controls, badges, tables, screenshots, and dialogs remain readable. No flash of incorrect theme.

## 7. Page templates

### 7.1 Homepage

Create a configurable section builder using reorderable theme settings or block patterns. Default order:

1. Compact hero/search area—not a huge image banner.
2. Featured categories as icon chips/cards.
3. Trending apps horizontal rail.
4. Latest updates two-column list on desktop, one column mobile.
5. Latest games.
6. Editor's choice.
7. Popular apps by real download/view data.
8. Latest blog guides.
9. Optional editable SEO introduction below listings.

App list rows should resemble a polished store result: 72–88px icon, title, developer/category, version, size, updated date, rating when real, and a small Download/View button. Avoid repeating a large green CTA on every card if it makes the page noisy.

Each section has View all, loading skeletons only when data is actually asynchronous, and server-rendered initial content for SEO.

### 7.2 App archive and taxonomy archive

- Breadcrumbs.
- H1 and editable taxonomy description.
- Sort: newest, recently updated, popular, rating, A–Z.
- Filters: category, platform, price, file type, Android requirement.
- Query state represented in clean GET parameters so pages are shareable.
- Responsive grid/list toggle saved locally.
- Standard paginated canonical pages as the foundation. Optional Load more enhances them, with real crawlable pagination links retained.
- Empty state with clear/reset filters.

### 7.3 Search

Global search supports Apps and blog posts with labeled result types. Live suggestions:

- Trigger after at least two characters and 250ms debounce.
- REST endpoint with maximum 8–10 items.
- Search title first, then developer/package name.
- Cache common queries briefly.
- Escape highlighting safely.
- Full keyboard navigation with ARIA combobox behavior.
- Cancel stale requests with `AbortController`.
- Rate limit abusive clients.
- Never query all posts.

Search results show icon, app name, developer, version, category, post type, and highlighted matching text.

### 7.4 Single app page

Build this exact information order:

1. Breadcrumbs.
2. App hero card: 120–144px icon; H1; short description; developer; verified/editorial labels; user/editor rating separated; current version; updated date.
3. Primary Download APK button with file size. Secondary official-store link when available.
4. Six-cell metadata grid: version, size, requirement, package, developer, price. Collapse gracefully on mobile.
5. Trust/provenance strip: hash available, scan status, source, last checked. Use factual labels only.
6. Screenshot gallery: horizontal scroll on mobile, lightbox dialog, image dimensions using WordPress responsive image APIs.
7. Optional video embed using privacy-enhanced mode where supported and click-to-load.
8. Article content with automatic but accessible Table of Contents generated from H2/H3 headings; allow editor disable.
9. What's New.
10. Technical details table.
11. Version history.
12. Download/install guidance block.
13. Safety notice and report link.
14. Related apps based on category/developer, excluding current app.
15. Real reviews/comments if enabled.

Desktop may use a 760px content column plus a 340px sticky sidebar. Sidebar can contain download card, app details, related apps, and ads. On mobile, never hide essential details in the sidebar; move them into the document flow.

The sticky mobile download bar must not obscure content, cookie controls, or browser UI. Include safe-area padding.

### 7.5 Version history page

Route: `/app/{slug}/versions/`.

Show current and older releases with version, date, size, minimum Android, file type, architecture, hash availability, changelog accordion, and download link. Paginate long histories. Add canonical and breadcrumbs. Do not index arbitrary download-token URLs.

### 7.6 Download interstitial

Route: `/download/{signed-token}/` or an equivalent rewrite that does not reveal filesystem paths.

Show:

- App icon/name/version.
- File name, type, size, SHA-256, signature hash if known.
- Scan/provenance status with timestamp.
- Install warning and source disclaimer.
- One clear final download button.
- Optional countdown disabled by default; if enabled, do not block accessibility and provide a no-JS link.

Security behavior:

- Token is signed, scoped to a version, expires, and is validated server-side.
- Local files stream through a safe handler or use protected server/CDN rules; prevent path traversal.
- External URLs use an allow/deny policy and a warning page.
- Count a download once using a privacy-aware short-lived token, not every request or bot hit.
- Send suitable headers: content type, disposition, length, nosniff, and cache policy.
- Never execute or inspect an uploaded APK on the WordPress web server.

### 7.7 Blog, pages, 404

- Blog cards use featured image, category, author/date, excerpt, and reading time.
- Standard page template offers full-width and sidebar options.
- 404 includes app search, popular categories, and recent apps; it must return HTTP 404.
- Author/date archives can be disabled or noindexed through an SEO plugin, not hacked out of templates.

- Homepage sections: enable, order, item count, selected categories.
- App page: sidebar, TOC, screenshots, ratings, reviews, sticky download bar.

Provide sensible defaults. Every setting must have sanitize callbacks, capability checks, reset controls, and live preview only where practical.

## 10. SEO and structured data

Make the theme compatible with Rank Math, Yoast SEO, and core sitemaps. Do not output duplicate title, meta description, canonical, Open Graph, or Twitter tags when an SEO plugin owns them.

Theme/plugin responsibilities:

- Semantic headings: exactly one visible H1 on normal templates.
- Breadcrumb UI and `BreadcrumbList` schema only when not already output by an SEO plugin.
- App schema using `SoftwareApplication` only from factual stored data.
- Include `name`, `operatingSystem`, `applicationCategory`, `softwareVersion`, `fileSize`, `dateModified`, offers, author/developer, screenshot, and real aggregate rating only when valid.
- BlogPosting schema for posts only when another SEO plugin does not provide it.
- Clean canonical archive pagination.
- Noindex internal search pages via SEO plugin integration or `wp_robots`.
- Download interstitial/token pages noindex and excluded from XML sitemaps.
- App, taxonomy, developer, and blog URLs included in core sitemaps.
- Proper 301 behavior if app slugs change, preferably through an SEO plugin hook.
- Descriptive image alt text editable per Media Library item; never keyword-stuff generated alt text.

Do not add FAQ schema unless the FAQs are visible and the current search-engine policy supports the intended use. Do not fabricate dates, downloads, authorship, reviews, or update claims.

## 11. Performance requirements

Targets on a representative mobile connection and uncached first view:

- Lighthouse Performance at least 90 on home/archive/single demo pages.
- Accessibility, Best Practices, and SEO at least 95.
- LCP under 2.5s, CLS under 0.1, INP under 200ms where lab tooling can approximate it.
- Initial theme CSS under 80 KB compressed; initial custom JS under 50 KB compressed, excluding WordPress core.
- No front-end jQuery dependency.
- No large SDKs loaded on normal requests.

Implementation:

- Use `wp_enqueue_script`/`wp_enqueue_style` with file-based versions from the build manifest.
- Add `defer` through supported WordPress script strategies.
- Split lightbox, reviews, filters, and search JS by page/feature.
- Use responsive WebP/AVIF generated by WordPress when available and always include width/height.
- Eager-load only the likely LCP image; lazy-load below-the-fold media.
- Cache app rails and expensive taxonomy counts; invalidate on relevant saves.
- Avoid N+1 metadata/term queries; prime caches.
- Paginate everything.
- Use object cache when available but do not require Redis.
- Keep CSS and markup resilient when cache/minification plugins combine assets.

## 12. Security and privacy checklist

Apply WordPress coding and security standards everywhere:

- Guard PHP files with `defined('ABSPATH') || exit;` where appropriate.
- Nonces protect state-changing requests, but also check capabilities and object ownership.
- Sanitize on input, validate business rules, escape on output at the last responsible moment.
- Use `esc_html`, `esc_attr`, `esc_url`, `wp_kses_post`, and allowlists according to context.
- Use prepared SQL and strict REST `permission_callback` functions.
- Rate-limit ratings, reports, search, downloads, and submissions.
- CSRF, XSS, SQL injection, SSRF, open redirect, path traversal, unsafe deserialization, unrestricted upload, IDOR, and privilege escalation must have explicit tests.
- No PHP execution in upload directories. Provide documented Apache and Nginx rules for APK storage.
- Do not expose absolute server paths, cloud credentials, API keys, stack traces, or signed source URLs.
- Remote requests use `wp_safe_remote_get`, short timeouts, size limits, redirect limits, and host validation.
- Log security-relevant failures without personal data or secrets.
- Include uninstall behavior that asks whether to retain content; never delete app posts/files automatically.
- Add privacy-policy helper text for ratings, reports, download counters, and analytics.

For gambling/casino APK categories, support age/responsible-gaming notices and configurable jurisdiction warnings. Do not present gambling as guaranteed income. The theme must not automatically generate misleading claims such as “100% safe,” “official,” “instant withdrawal,” or “guaranteed earnings.”

## 13. Accessibility and internationalization

- Meet WCAG 2.2 AA.
- Full keyboard operation for menus, filters, lightbox, tabs, accordions, search suggestions, rating controls, and dialogs.
- Visible focus styles using `:focus-visible`.
- Correct labels, descriptions, error messages, live regions, and focus movement.
- Respect `prefers-reduced-motion`.
- Never rely on color alone.
- Use real buttons for actions and links for navigation.
- Mark decorative SVGs `aria-hidden`.
- Every PHP string translated with the correct text domain.
- Include POT generation script.
- RTL support through logical CSS, tested with Urdu and Arabic.
- Dates, numbers, bytes, and currencies use WordPress locale helpers.

## 15. Development phases for Cursor

Work phase by phase. At the end of each phase, run the checks, show changed files, report remaining issues, and commit with a clear message if Git is available. Do not claim completion while tests fail.

### Phase 0 — Discovery and plan

1. Inspect the workspace and existing files.
2. Confirm whether this is a new repository or an existing WordPress project.
3. Create `IMPLEMENTATION_PLAN.md` mapping every requirement to theme/plugin files and tests.
4. Record assumptions. Ask only questions that block architecture, such as whether local APK hosting is legally and operationally required.

### Phase 1 — Scaffolding

Create both packages, Composer autoloading, build scripts, PHPCS, PHPUnit, WordPress test setup, and CI workflow. Add activation/deactivation hooks to the plugin. Produce installable ZIP commands.

### Phase 2 — Data layer

Register post type, taxonomies, post meta, capabilities, version table, repository, service, migrations, REST schemas, and fixtures. Write unit/integration tests before UI work.

### Phase 3 — Admin publishing UI

Build editor panels, version manager, media gallery, validation, notices, setup wizard, and demo importer. Confirm keyboard access and role permissions.

### Phase 4 — Theme foundation

Build theme setup, `theme.json`, header, footer, navigation, layout primitives, typography, light/dark tokens, responsive behavior, and accessibility helpers.

### Phase 5 — Discovery pages

Build homepage, app archive, taxonomy/developer archives, filters, search results, live search, pagination enhancement, and reusable app cards.

### Phase 6 — App and download pages

Build single app, gallery/lightbox, TOC, version history, related apps, reviews, report form, download interstitial, signed links, secure local/external delivery, and download counting.

### Phase 7 — SEO, compatibility, and migration

Add schema, sitemap/robots behavior, Yoast/Rank Math compatibility, breadcrumbs, Appyn dry-run migration, CLI commands, and cache invalidation.

### Phase 8 — QA and release

Run all automated and manual tests, generate demo screenshots, validate ZIP installs on a clean WordPress instance, write documentation, and create release ZIPs with no dev dependencies, source maps, secrets, demo APK files, or OS junk.

## 16. Testing and definition of done

Required automated checks:
